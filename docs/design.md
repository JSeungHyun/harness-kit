| | |
|---|---|

## 0. 결정

| | 결정 | 근거 |
|---|---|---|
| 형태 | **한 레포 · 두 모듈(evidence · graph) · 데이터 미이전** | 따로 다듬은 두 레포가 흐름·ponytail·규칙 위치 세 곳에서 이미 충돌했다. 옮기는 것은 도구·템플릿·규칙이고, 프로젝트의 기록은 그 프로젝트에 둔다(운영 중인 프로젝트의 기록 222건에는 실제 사번 · 그 프로젝트의 경로 · 도메인 용어가 들어 있다) |
| SETUP | **신규 구축 / 기존 이식 프로필**로 갈린다 | 도구가 아니라 시작 상태가 다르다 — 소급할 과거, 이미 있는 지시 파일, 테스트 기준선 |
| 흐름 | superpowers 가 베이스. **계획 문서는 인계·다세션일 때만** (§3) | 운영 세션 실측: 작은 변경·운영 요건에는 계획이 비용이고, 절차가 이미 적혀 있으면 계획은 그 복사본이다 |
| 관문 | **작업 종료 보고에 건다** — 계획의 마지막 태스크가 아니다 (§3) | 계획 유무와 관문을 분리한다. 계획이 있으면 마지막 태스크가 보고를 부르고, 없으면 보고가 곧 관문이다 |
| 완료 증거 | **작업 종류별** — 코드는 verify(기준선 포함), 운영·기록·조사는 각자의 증거 (§4) | 운영 세션 실측: 운영 작업과 상시 실패 14건은 「이번 실행의 testcase」 게이트와 양립하지 않는다 |
| ponytail | 프로젝트 범위 `PONYTAIL_DEFAULT_MODE=off`, 코드를 바꾼 보고 직전에 `/ponytail-review` | 10-02 결정 유지. 운영 세션: off 여도 충돌이 약하다 |

| 규칙 위치 | `.claude/rules/harness.md` · `.claude/rules/graph.md` | `CLAUDE.md` 유무 · 8.3 단축 경로와 무관하게 로드됐다(agent-harness 실측 3조건) |

## 1. 두 모듈

| 모듈 | 막는 실패 | 도구 |
|---|---|---|
| **evidence** | 완료를 거짓 보고한다 · 묻지 않고 넘어간 가정이 묵는다 · 같은 실패를 반복한다 | `verify` · `decision-check` · `lesson-append` · `lesson-promote` · `state-check` · `policy-apply` |
| **graph** | 같은 것을 두 번 조사한다 · 사용자의 말과 코드의 이름 사이 다리가 없다 | `graph-find` · `graph-append` · `graph-alias` · `graph-hook` · `graph-view` · `graph-measure` |
| 설치 | — | `detect` · `install-mode` · `scan-shared` |

graph 에서 **뺀 것**: `db-guard`·`sql-template-check`·DB 코멘트 절(특정 DB · 특정 프로젝트의 운영 정책), `commit-index`(실행 5회)·`spec-toc`(7회) — 운영 세션 48회 실측으로 범용 값이 없다.

## 2. 장부 분담 — 한 곳에서 정한다

| 무엇 | 어디 | 로드 |
|---|---|---|
| 사실 · 함정 · 인과 · **기각한 대안 한 줄** | 그래프 `note` | 그 주제를 물을 때만 |
| 하다 만 것 | 그래프 `note` 의 `⏸` | 훅·조회가 랭킹과 무관하게 붙인다 |
| 행동을 바꿔야 하는 것 | 규칙(`.claude/rules/`)·프로젝트 지도(`AGENTS.md`/`CLAUDE.md`) | 매 세션 |
| 반복 실패(규칙이 되기 전) | `lessons` | 조회로만 — 승격 후보를 낸다 |
| 묻지 않고 정한 가정 | `decisions` | 조회로만 — 14일 묵으면 경고 |
| 사용자 선호 | 메모리 | 세션 시작 |

**승격 방향은 한 방향이다 — 그래프·lessons → 규칙.** 기준: 「다음 세션이 이걸 안 읽으면 같은 실수를 하나 → 그러면 규칙」. 근거(운영 세션 2026-09-10): 새 탐색 방법을 그래프에만 적었더니 바로 다음 턴에 그 방법을 쓰지 않았다.

⛔ `note` 와 `lessons` 를 합치지 않는다 — note 는 주제에 걸려야 값이 있고, lessons 는 주제와 무관하게 적용돼야 한다.

## 3. 흐름 — 계획 문서와 관문

| 작업 | 계획 문서 | 근거 |
|---|---|---|
| 작은 변경 (파일 1~3, 순서 없음) | 쓰지 않는다 | 🔬 운영 세션 실측 |
| 여러 파일 · 순서 의존 | `TodoWrite` 로 단계만. 절차가 이미 적혀 있으면(스킬·문서) 그것을 따른다 | 🔬 운영 세션 실측 |
| 운영 요건 (현업 대기 · 코드 변경 없음) | ⛔ 쓰지 않는다 — 실행·확인 쿼리를 본문에 먼저 | 🔬 운영 세션 실측 (2026-09-07 지적 2회) |
| 구현을 다른 세션·서브에이전트에 인계 · 여러 세션에 걸침 | superpowers `writing-plans`. 옮기는 코드는 출처로 가리키고 새 로직만 적는다 | 🤔 추론 — 받는 쪽은 내 컨텍스트가 없다 |

- ⛔ brainstorming 의 종료 조건(「writing-plans 호출」)보다 위 표가 우선한다
- **되돌리기 어려운 작업은 착수 전에 제안하고 승인받는다** — 데이터 삭제·이력 재작성·운영 반영·레포 밖으로 나가는 작업·비밀값
- 승인된 일을 실행하는 동안에는 묻지 않는다 — 가정은 `decisions` 에 적고 진행한다

**관문 = 작업 종료 보고 (`final-gate` 스킬).** 작업을 끝냈다고 보고하기 직전에 매번 거친다.

```
1. 코드를 바꿨으면 /ponytail-review — 과설계만 본다. 지적마다 걷어내거나 남기는 이유 한 줄
2. 완료 증거 — §4 의 작업 종류별. 없으면 없다고, 왜 없는지
3. 보고 한 세트
   ① 작업 파일 목록 (생성/수정/삭제, 전체 경로)
   ② 기록 — 그래프(요구→용어·파일·함정·기각한 대안) · decisions · lessons · 낡은 기록 supersedes. 남길 게 없으면 그 판단을 한 줄로
   ③ 완료 증거 — 2 의 출력 그대로. 「통과했다」로 줄이지 않는다
   ④ 못 한 것 · 막힌 것 → ⏸ 로 기록
4. 브랜치를 마무리하는 보고(merge·PR 직전)면 /security-review 1회 → finishing-a-development-branch
```

⚠️ `/ponytail-review` 는 과설계만 본다. 정확성은 완료 증거가 맡는다 — 둘을 섞으면 과설계 리뷰 통과를 동작이 맞다는 뜻으로 읽게 된다.

⛔ **기록의 두 장치** (운영 세션 실측 — 「기록해라」만 있으면 조용히 건너뛴다):
- 남길 게 없다고 판단했으면 **그 판단을 한 줄로 밝힌다** — 침묵을 불가능하게 만든다
- 기능을 바꿔 기존 기록이 낡았으면 **그 자리에서 고친다.** 새 기록 추가로 갈음하지 않는다 — **다음 세션의 나는 그 불일치를 사실로 믿는다.** 기준: 「이 기록을 그대로 믿고 작업하면 틀리나」

⚠️ 이 장치들이 충분하다는 증거는 없다 — 운영 세션도 여전히 가끔 빠뜨린다. 수동 기록이 가장 약한 고리다.

⛔ **이 표의 한계** — 「계획 없이 문제가 없었다」는 「계획이 무용하다」와 같지 않다. 계획을 썼더라면은 반사실이라 A/B 가 안 된다. 인계 행은 사례가 없는 추론이다.

## 4. 완료 증거

| 작업 | 증거 | 판정 |
|---|---|---|
| 코드 변경 | `node .harness/tools/verify.mjs` | 기계 — exit 0 |
| 운영 데이터 · 설정 | 실행·확인 쿼리와 전/후 결과를 본문에 (실행은 사용자일 수 있다) | 사람 |
| 기록 변경 | `node .harness/tools/graph-find.mjs --check` | 기계 — exit 0 |
| 조사 · 측정 | 정답 라벨 n건 대조 + 검증한 범위 | 사람 |

**verify 의 검사 종류** (`.harness/harness.json` 의 `checks[]`):

| `kind` | 통과 조건 |
|---|---|
| `junit-xml` | 명령 exit 0 **또는 실패가 전부 기준선 안**, 이번 실행이 쓴 XML 에 실행된 testcase ≥ 1, 기준선 밖 실패 0 |
| `exit-code` | 명령 exit 0 — 도구 자체 검사(`--check` 류)도 여기 |
| `file-unchanged` | 생성 명령 exit 0, `git status --porcelain -- <evidence>` 가 비었다 |
| `output-match` ⭐신규 | 명령 exit 0, stdout 이 `expect`(정규식)에 맞는다 — 검증 쿼리 결과 |

**알려진 실패 기준선** ⭐신규 — `.harness/baseline/<검사 id>.txt`, 한 줄에 `classname::name` 하나:

- 기준선 안의 실패는 실패로 치지 않고 개수만 보고한다
- 기준선 밖의 실패가 하나라도 있으면 실패다
- 기준선에 있던 testcase 가 통과하면 「기준선을 줄인다」를 안내한다 — 실패로 만들지 않는다(검사는 드물게 울려야 신호다)
- `node .harness/tools/verify.mjs --baseline` 이 지금의 실패를 기준선으로 쓴다. ⛔ 기존 이식에서 **사용자가 「원래 있던 실패」라고 확인한 뒤에만** 돌린다
- 명령이 exit 0 이 아니어도 **기준선 안 실패가 1건 이상이고 기준선 밖 실패가 0** 이면 통과다 — 실패 테스트가 있으면 러너는 늘 exit 1 을 낸다. ⛔ 실패 0 인데 exit 1 이면 실패다 — 「전부 기준선 안」을 빈 집합에도 참으로 읽으면 깨진 러너를 통과시킨다 (구현 중 발견)

## 5. graph 모듈

- 도구 6개는 `context-graph` 의 **동작을 그대로** 옮긴다 — 토크나이저·채점·정본 1장 규칙·침묵 문턱 `s ≤ 2`·1단 탈출구·`⏸` 노출·`supersedes` 제외. **깨지면 안 되는 8개와 바꾸면 안 되는 훅 출력 문장은 `docs/graph-port.md`**
- 예외는 훅 **출력 크기** 하나 — 운영 재생(실제 프롬프트 401건)으로 2단은 점수 상위 10건, 1단 카드 용어는 채점 규칙 ③, 2위 카드는 정본·사전만 전문으로 바꿨다. 판정·순위는 그대로이고 주입은 −62% 다(`graph-port.md` §5). 운영 데이터 대조에서 그래프는 도구 호출 −91% · 정답 8/8 vs 4/8 이었다(README §실측)
- 저장: `.harness/graph/requests.jsonl` — 도구 파일 기준 상대경로(`../graph/`)로 찾는다. 테스트는 `HARNESS_GRAPH_STORE` 로 바꾼다
- 훅: `policy/graph-hook.json` 을 `policy-apply --with graph-hook` 으로 병합한다. **켜는 조건: 살아있는 기록 20건 이상 + `--check` exit 0 + 상위 3 기록 점유 < 50%** (질의 집합 — 이슈 제목 export — 이 있으면 `graph-measure` 로 잰다. 없으면 앞의 둘만, 보고에 「독점 미측정」)
- ⛔ **개인 식별자(사번·이름·연락처)를 기록하지 않는다** — 공유 모드에서는 그대로 커밋된다
- `graph.md` 의 판단 규칙 상위 5 — 예시 낱말 금지(전 필드가 색인된다) · 행동은 지침, 사실은 그래프 · 원천 3분류(사람이 쓴 것만 옮기고, 코드 구조는 도구로 조회, 해석·인과는 자동 추출 금지) · 근거 등급(사슬을 다 못 읽었으면 `⚠️ 미확정` · **새 원천도 단일 증거다** — 기존 기록과 어긋나면 어느 쪽도 먼저 믿지 않고 데이터로 재판정) · 같은 주제가 2건 이상이면 `정본: ` 1건으로 통합. 순서는 사고 **빈도**순이고, 피해는 근거 등급 위반이 가장 크다(거짓이 사실로 유통된다). 상세는 `docs/graph-port.md` §3
- 「⚠️ 없는 기록은 확인차 다시 보지 않는다」의 예외 — 새 원천(문서·DB 코멘트·담당자 답변)이 기존 기록과 다른 값을 말할 때. 운영 세션에서 낡은 기록을 믿어 틀린 3건 중 가장 많이 작동한 탈출구는 사용자 지적이었다
- 신규는 `supersedes` 가 잦다 — 설계 때의 용어가 구현에서 바뀐다. 종료 보고의 기록 단계에서 「설계 용어를 구현 이름과 맞췄나」를 본다

## 6. 설치 — 프로필과 모드

**판별** — `node <kit>/tools/detect.mjs <대상>` 이 사실과 제안값을 낸다. Claude 는 제안을 사용자에게 확인받는다. 비대화형 실행이면 제안값으로 진행하고 보고에 남긴다.

| 사실 | 신규 제안 | 기존 제안 |
|---|---|---|
| 커밋 수 · 추적 소스 파일 수 | 커밋 < 20 이고 소스 < 50 | 그 밖 |
| 설치 모드 | 로컬 전용 (공유는 사용자가 고른다) | 로컬 전용 |

함께 내는 사실: 지시 파일(`CLAUDE.md`·`.claude/CLAUDE.md`·`CLAUDE.local.md`·`AGENTS.md` — 추적 여부, `@AGENTS.md` import 여부), 다른 도구 규칙(`.cursor/rules`·`.github/copilot-instructions.md`), 테스트 단서(`package.json` test · `gradlew` · `pom.xml` · `pytest`), 설치 경로가 git 에 무시되는가, 기존 하네스(`.harness/`) · 기존 context-graph 설치(`tools/graph/requests.jsonl`).

| | 공유 | 로컬 전용 |
|---|---|---|
| git | 무시되는 설치 경로만 저장소 `.gitignore` 에 부정 규칙(`!.claude/` · `!.harness/` · `!AGENTS.md` · `!CLAUDE.md`) + `.claude/settings.local.json` 은 다시 무시 | 설치 경로를 `.git/info/exclude` 에 |
| 설정 | `.claude/settings.json` · 플러그인 설치는 `--scope project` | `.claude/settings.local.json` (`policy-apply --local`) · 플러그인 설치는 `--scope local` — ⛔ 병합은 `enabledPlugins` 의 명시적 `false` 를 보존한다. 로컬 모드에서는 정책과 중복 처리가 같은 파일이라, 덮으면 재실행 때 중복 플러그인이 되살아난다 (구현 중 발견) |
| 장부 | `docs/harness/{decisions,lessons}.md` | `.harness/state/{decisions,lessons}.md` |
| 확인 | `git check-ignore` 로 설치 경로가 추적 가능한지 | 무시되는지 |
| 민감 정보 | ⛔ **커밋 전마다** `node .harness/tools/scan-shared.mjs` — 패턴은 `.harness/scan.json`(기본: 사번 형식 · 내부 도메인 · DB 접속(URI · CLI 인자) · 이슈 번호(`KEY-123` · `<도구> #123`) · 실명이 든 파일명(뒤에 버전 토큰 포함) · 하이픈 복합 번호(전화 · 계정 복합키, ISO 날짜 제외) · 자격증명 낱말 — 패턴마다 「놓치는 것」을 적는다). ⛔ **기본 패턴은 프로젝트 형식을 모른다** — 운영 세션 실측에서 기본 6종 중 4종이 실제 값을 못 잡았다(공개 TLD 사내 도메인 · CLI 형태 접속 · `<도구> #번호` · 이름 뒤 버전 토큰). 그래서 `"reviewed": false` 인 동안 scan-shared 가 「기본 패턴 그대로다」를 경고하고(exit 는 그대로), 설치 때 사용자와 사번 · 내부 호스트 · 이슈 형식을 맞춘다. `install-mode share` 가 pre-commit 훅으로 건다(이미 훅이 있거나, `core.hooksPath` 가 저장소 git 디렉터리 밖 — 전역 훅 폴더 · 추적되는 `.husky` — 이면 쓰지 않고 안내만. 전역 폴더에 쓰면 다른 모든 레포의 커밋이 실패한다 — 보안 검토) | — |

공유를 고르는 것은 사용자다. SETUP 은 위험(기록에 쌓이는 사번·실명·이슈 번호·데이터 분포 수치)을 보여 주고 묻는다. 비대화형 실행이면 로컬 전용이다.

**지시 파일** — ⛔ 기존 내용을 고치거나 옮기지 않는다. 더하는 것은 import 한 줄뿐이고 사용자 승인을 받는다.

| 대상에 있는 것 | 공유 | 로컬 전용 |
|---|---|---|
| 없음 | `AGENTS.md`(프로젝트 지도 골격) + `CLAUDE.md`(`@AGENTS.md`) 를 만든다 | `CLAUDE.local.md`(지도 골격)를 만든다 |
| `CLAUDE.md` (또는 둘 다, import 있음) | 그대로 | 그대로 |
| `AGENTS.md` 만 | `CLAUDE.md` 에 `@AGENTS.md` 한 줄 — 8.3 단축 경로 세션에서도 읽힌다 | `CLAUDE.local.md` 에 `@AGENTS.md` 한 줄 |
| 둘 다, `CLAUDE.md` 가 import 안 함 | `AGENTS.md` 가 안 읽히고 있다고 보고하고 import 한 줄을 제안 | 같음 |

**기존 이식 — 이미 있는 것을 쓰는 법**

| 이미 있는 것 | 옮길 자리 |
|---|---|
| 지시 파일·README 의 빌드·테스트 명령 | `harness.json` 의 `checks` |
| 용어 사전 · 인수인계 문서 | 그래프 `graph-alias` (출처를 note 에) |
| 지시 파일의 금지·주의 규칙 | ⛔ 옮기지 않는다 — 이미 상시 로드되는 행동 규칙이다. 과거 실패와 이어지면 lessons 의 「무엇이 막는가」에 그 절을 적는다 |
| 기존 가정 장부 · TODO | 그 경로를 `harness.json` 에 |
| 실패 중인 테스트 | 사용자가 「원래 있던 실패」라고 확인하면 `verify --baseline` |

소급 원천의 순서 (운영 세션 실측 값 순): 이슈·티켓 전수 > 인수인계·가이드 문서 > 담당자 확인(단위당 값이 가장 크다 — 설치 뒤에도 대화 중에) > DB 코멘트(⛔ 복사하지 않고 조회 명령만 지도에) > 커밋 이력(수정 커밋 → lessons 2~3건, 요구 단위 → 그래프 3~5건 — 144건 중 커밋 유래는 6건으로 기여가 낮다).

- **기록 단위는 「이 용어들이 같은 질문에서 함께 필요한가」** — 함께면 주제 기록 1건, 갈리면 2~3건. ⛔ 용어 사전을 한 건에 몰아넣지 않는다(광역 기록이 적중을 독점한다). ⛔ 용어 1개짜리 alias 로 잘게 쪼개지도 않는다(`req` 가 빈약해 정확일치를 못 받는다)
- ⛔ 커밋에서 만든 기록은 `terms`(현업 용어 → 식별자)를 사람이 채워야 값이 있다 — 제목만 넣으면 0 이다
- 훅 문턱은 🔬 **소급 측정값이다** (운영 세션, 이슈 제목 질의 530건 · 기록을 기록순 앞 N건으로 잘라 같은 채점): 상위 3 기록의 확신 점유 10건 74% → **20건 42%** → 50건 52%(재상승 — 광역 기록 유입, 추정) → 110건 33%. 확신율은 110건에서 85%로 포화. ⇒ 독점은 단조 감소하지 않는다 — 건수는 대리 지표이고 조건은 「상위 3 점유 < 50%」다. 켠 뒤에도 잰다
  - ⚠️ 측정의 한계: 기록은 나중에 제자리 수정되므로 「앞 N건」 ≠ 「N건 시점의 그래프」 — 실제 초기 확신율은 이보다 낮았을 것이다. 독점률 곡선(「기록이 적으면 소수가 독점한다」)은 구조적 성질이라 내용 수정과 무관하게 유효하다

**신규 — 처음부터 쌓는 법**: 소급 없음. 브레인스토밍 스펙이 있으면 현업 용어 → 계획한 식별자를 alias 로 적되 note 에 「설계 용어 — 구현 후 재확인」. 첫 테스트 전에는 verify 가 「실행된 테스트가 0개」로 실패하는 것이 정상이다 — 보고에 그렇게 적는다.

**기존 context-graph 설치가 있으면** — ⛔ 데이터를 옮기지 않는다. 감지해서 보고하고, 그래프 모듈은 설치하지 않는다(기존 도구가 그 프로젝트의 그래프다). 전환은 범위 밖.

## 8. 원칙

| 원칙 | 왜 |
|---|---|
| 자동 로드되는 층은 규칙 파일 둘만 더한다 | 쌓일수록 매 세션 비용 |
| 값이 아니라 명령을 적는다 | 재생성되는 값은 낡는다 — DB 코멘트를 베끼지 않는다 |
| 검증 안 된 것을 적지 않는다 | 딱지 — 지금은 전부 설계안 |
| 장부는 성격마다 하나 | §2 — 같은 사건이 두 장부에 다르게 적히면 정본이 사라진다 |
| 자동 추출하지 않는다 | 판단을 거쳐 기록한다 |
| 의존성 0 · Node 22+ · OS 무관 | 셸은 플랫폼 기본, 경로는 `node:path`, 줄바꿈은 `\r?\n` |
| 검사는 드물게 울려야 신호다 | correctness(verify · 무결성 · 입력 거부)만 exit 1 |
| 자동 승인(allow)에는 인자로 쓰기·실행에 닿지 않는 명령만 | allow 는 사람의 확인을 건너뛴다(보안 리뷰) |
| 대상의 기존 파일을 옮기거나 덮어쓰지 않는다 | 규칙은 새 파일, 설정은 병합, 지시 파일엔 import 한 줄만 |
| 특정 프로젝트 이름 · 개인 식별자를 넣지 않는다 | 범용 템플릿이다 |

## 9. 검증

1. **단위** — 두 모듈의 도구 전부 `node:test`. graph 도구는 옮기기 **전에** 원본 동작으로 특성 테스트를 쓰고, 옮긴 뒤 같은 테스트가 통과해야 한다
2. **결정론 실측** (`node proof/run.mjs`) — 하네스 없이 vs 있을 때: 거짓 완료(테스트 0개 · 직전 XML · 기준선 안/밖 실패), 장부, 설정 병합(공유/로컬 · 훅), 그래프(append→find · 훅 침묵·탈출구 · ⏸), 설치 모드(모의 전역 gitignore 를 공유가 이기는가 · 로컬이 숨기는가), 판별(신규·기존 합성 저장소)
3. **새 세션 실측** (`--claude`) — 규칙 2개가 로드되는가(양성 2 · 음성 1), ponytail 이 꺼졌는가
4. ⭐ **SETUP 종단 실측** (`node proof/setup-e2e.mjs`) — 새 Claude 세션이 SETUP 을 처음부터 끝까지 따르는가. 신규·기존 합성 대상 각각에 설치시키고 `proof/check-install.mjs` 가 결과를 프로필별 기대와 대조한다. 실측이 사용자 전역 상태에 남긴 것(프로젝트 범위 플러그인 기록)은 되돌린다

## 11. 범위 밖

- 기존 context-graph 설치를 이 구조로 전환하는 자동화 — 감지·보고만 한다
- graphify — 큰 레거시 코드베이스에 한해 선택. 쓸 때는 `--code-only`, 안내는 `.claude/rules/`, `reflect` 를 쓰지 않는다(장부는 하나)
- DB 코멘트 · 운영 DB 가드 도구 — 스택·정책마다 다르다. 프로젝트가 직접 둔다
