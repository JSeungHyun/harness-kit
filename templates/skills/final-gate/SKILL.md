# 관문 — 작업 종료 보고

> 상태: **설계안**

보고 직전에 **매번** 돈다. 계획이 있으면 그 마지막 태스크가 이 스킬을 부르고, 없으면 보고가 곧 관문이다.

## 절차

1. **코드를 바꿨으면 범위 검토 → `/ponytail-review`** (→ 아래 조건이면 `/code-review`). 걷어내거나 고쳤으면 2 를 그 뒤에 돈다 — 관문 훅(Stop)이 이번 턴에 이 호출들과 마지막 코드 변경 뒤의 verify 가 있는지 보고, 빠지면 한 번 되돌린다
   - **범위 검토** — 서브에이전트(sonnet)에 이번 턴과 직전 턴의 **사용자 말 원문**, 이번 작업이 바꾼 부분의 `git diff` 만 주고 묻는다: 「사용자가 요청하지 않았는데 들어간 변경 — 특히 화면에 보이는 문구 · 동작 — 을 `파일: 무엇` 한 줄씩. 요청에서 자연스럽게 따라 나오는 것(구현 세부 · 테스트 · 문서와 기록 갱신)과 확실하지 않은 것은 빼고, 없으면 「없음」」. 내 요약이 아니라 원문을 준다 — 넣은 쪽은 그 변경을 요청의 일부로 읽는다. 걸린 것은 걷어내거나, 남기면 보고 맨 앞에 **요청 밖 변경**으로 밝힌다
   - **`/ponytail-review`** — 과설계만 본다. 지적마다 걷어내거나, 남기는 이유를 한 줄 적는다
   - **`/code-review`** — ⭐ **바꾼 코드가 verify 의 테스트로 실행되지 않을 때만** — 바꾼 파일이 `.harness/harness.json` 검사의 `covers`(그 검사가 돌리는 코드의 glob) 어디에도 들지 않으면 정확성 증거가 없는 자리다(예: Java 를 바꿨는데 검사는 `npm test` 뿐). verify 가 첫 줄에 「코드 검사 없음」을 내면 모든 코드 변경이 여기다. 지적마다 고치거나, 남기는 이유를 한 줄 적는다. 테스트가 그 코드를 돌리면 부르지 않는다 — 정확성은 verify 가 맡는다
2. **완료 증거** — 작업 종류별로. 없으면 없다고, 왜 없는지 적는다

   | 작업 | 증거 |
   |---|---|
   | 코드 변경 | `node .harness/tools/verify.mjs` — exit 0 이 아니면 보고하지 말고 고친다 |
   | 운영 데이터 · 설정 | 실행·확인 쿼리와 전/후 결과 |
   | 기록 변경 | `node <graph-tools>/graph-find.mjs --check` — exit 0 · 기록을 고친 **뒤에** 돌린다 |
   | 조사 · 측정 | 정답 라벨 n건 대조 + 검증한 범위 |

3. **보고 한 세트**
   1. 작업 파일 목록 — 생성/수정/삭제, 전체 경로
   2. 기록 — 그래프(요구 → 용어·파일·함정·기각한 대안, <graph-rules> — 이 저장소의 지식만) · 묻지 않고 정한 가정(decisions 1절, 그리고 `node .harness/tools/decision-check.mjs`) · 반복 실패(`node .harness/tools/lesson-append.mjs`). 설계 용어를 구현 이름과 맞췄나 본다. 기록의 두 장치:
      - **남길 게 없으면 그 판단을 한 줄로** 밝힌다 — 침묵을 불가능하게 만든다. 그래프는 줄 맨 앞에 이 머리말 그대로 `그래프: 기록 안 함 — <이유>`. 관문 훅은 **코드를 바꾼 턴에만** 이 줄, 또는 이번 턴에 기록 파일이 바뀌었고 그 뒤에 끝난 `--check` 를 본다(문서 · 조사 · 운영 턴은 판단 한 줄만 쓰고 훅은 보지 않는다) — 기록을 검증한 뒤에 썼는지는 보지 못한다
      - 기능을 바꿔 기존 기록이 **낡았으면 그 자리에서 고친다**(그래프는 `supersedes`). 새 기록 추가로 갈음하지 않는다 — **다음 세션의 나는 그 불일치를 사실로 믿는다**. 기준: 「이 기록을 그대로 믿고 작업하면 틀리나」
   3. 완료 증거 — 2 의 출력 그대로. 「통과했다」로 줄이지 않는다
   4. 못 한 것 · 막힌 것 — 그래프에 `⏸` 로 기록한다
4. **브랜치를 마무리하는 보고(merge·PR 직전)면** `/security-review` 1회 → `finishing-a-development-branch`

## 하지 않는 것

| 하지 않는다 | 왜 |
|---|---|
| 증거 없이 「끝났다」 | 종료코드·러너 요약은 테스트 0개를 통과시킨다 |
| ponytail-review 통과를 「동작이 맞다」로 읽기 | 과설계만 본다. 정확성은 완료 증거(테스트가 그 코드를 돌리지 않으면 `/code-review`), 요청 범위는 범위 검토가 맡는다 |
| verify 녹색을 「바꾼 코드가 맞다」로 읽기 — 검사가 그 코드를 돌리지 않을 때 | verify 는 검사 목록만 증명한다. Java 4파일 변경에 `npm test` 만 녹색이던 턴에서 `/code-review` 가 실제 결함 6건을 냈다(2026-11-04 실전) |
| ponytail 모드를 켜고 작업 (프로젝트 지시 파일이 켜라고 정했으면 그쪽) | superpowers 의 설계·질문 단계와 충돌한다. 리뷰만 부른다 |
| `/security-review` 를 보고마다 | 브랜치를 마무리할 때 한 번이다 |
| 파일 목록만 보고하고 기록을 건너뛰기 | 둘은 한 세트다 — 다음 세션은 기록만 본다 |
